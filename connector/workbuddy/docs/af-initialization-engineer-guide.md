# AF 初始化试用版：工程师使用指南

适用范围：深信服 AF 8.0.107；通过 WorkBuddy 连接 SangforBox `af-workbench` MCP。试用版用于形成可审核的初始化设计、分阶段配置、回读核对和现场反馈。实际业务效果需要在现场验证。

## 从对话开始

可以直接对 WorkBuddy 说：“我要初始化这台 AF，请引导我完成设计。”不需要一次备齐资料。文字说明、接口表和拓扑图可以先给其中一种，后续逐步补充。WorkBuddy 会先确定设备、建立案例并返回 `case_id`，随后读取设备现状；请保留该编号，后续反馈沿用同一案例。

WorkBuddy 会围绕以下内容逐步询问，每轮通常只问当前最关键的几项：

| 内容 | 现场需要提供或确认的事实 |
|---|---|
| 部署与拓扑 | AF 所在位置、部署模式、上下游设备和连接关系 |
| 接口与管理 | 接口用途、IP/掩码、所属区域、管理路径及可能的中断窗口 |
| 业务范围 | 内外网方向、业务网段、服务器和用户保护范围 |
| 路由 | 目的网段、下一跳、出接口；是否需要默认出口 |
| NAT | 哪些流量需要转换、转换地址和方向 |
| 策略 | 安全防护与应用控制的范围、动作、顺序和启用状态 |
| 保留方式 | 是否保留现有配置，同名对象如何处理 |

例如，工程师先说“AF 在核心交换机和出口路由器之间，内网接 eth2，出口接 eth1”，WorkBuddy 会记录这些信息，再追问地址、区域和业务网段。接口名只作为标识；内外方向必须由工程师确认。工程师可以随时说“刚才 eth1 的地址要改成……”，设计版本会更新，受影响的计划需要重新生成。

资料完整后，WorkBuddy 会展示一份设计表，逐项标记“工程师确认”“设备实测”或“试用建议”。请先核对拓扑、地址、策略范围、启用状态和可能中断管理连接的变更，再确认设计版本。未解决的问题会留在待确认清单，不进入设备执行计划。

## 试用默认建议如何处理

WorkBuddy 会检查出口路由。AF 8.0.107 产品资料说明：静态 IP 接口填写下一跳后，不会自动生成默认路由。如果设计要求经 AF 三层转发到出口，现有配置又没有合适的默认或其他有效路由，WorkBuddy 会建议补充 `0.0.0.0/0`，请工程师确认下一跳和出接口。自动或动态路由、透明部署等情况需要按现场设计判断。

未提供 NAT 需求时，WorkBuddy 会根据拓扑询问哪些流量需要地址转换；转换地址必须由工程师确认。未提供安全防护细节时，会先确认“全拒绝”指未匹配业务流量拒绝、威胁检测阻断，还是两者，再提出具体方案。

AF 8.0.107 产品资料记载设备默认存在一条拒绝所有服务或应用的应用控制策略。本试用版会提出至少一条**针对已确认业务范围的放通规则**，并检查其实际顺序、区域、应用范围和启用状态。请确认这条规则允许的具体流量；不会把“默认放通”解释成所有流量放通。

## 分阶段实施与现场核验

WorkBuddy 按管理、接口与区域、网络对象、路由、NAT、安全防护、应用控制的依赖顺序处理需要变更的配置。每项变更都先读取现状、提出必答问题、生成计划，向工程师展示影响和恢复方法。工程师确认该计划后才执行；执行后立即回读。

回读会区分三种结论：

- **已验证**：设备返回的相关配置与计划字段一致。
- **需人工复核**：设备返回不足以证明全部字段生效，或存在差异。工程师核查后可记录人工处理结论与原因。
- **结果未知**：写入过程超时或异常，先读取设备现状；不能盲目重试。

接口连通、业务访问、NAT 命中和安全策略效果还需要现场测试。建议工程师在实施记录中写明测试源、目标、时间、预期和实际结果。静态配置回读通过不代表业务流量已经验证。

## 调整后的反馈与 CSV

现场调整完成后，对 WorkBuddy 说：“对案例 `<case_id>` 做初始化反馈。我调整了……，原因是……”。WorkBuddy 会通过 MCP 重新读取设备，生成三列对照：实施前、工具实施后、当前配置。工具计划之外新增或删除的对象也会列出，标记为需要工程师确认的现场变化。

先确认差异表中的对象和变化是否准确，再填写 WorkBuddy 提供的 CSV。每行对应一项配置；即使没修改，也要评价。需要填写：

| CSV 列 | 填写方式 |
|---|---|
| `difference_confirmed` | `yes`、`no` 或 `uncertain`，表示差异是否属实 |
| `satisfaction` | `satisfied` 或 `unsatisfied` |
| `reason` | 不满意时必填，说明原因；可写需求理解、默认方案、字段、顺序、执行或现场变化 |
| `comment` | 可选，写明建议做法和现场验证结果 |

保留 `case_id`、`item_id` 和 `review_hash` 等系统生成列。WorkBuddy 将填写后的 CSV 交给 MCP 校验并保存。如果设备在生成 CSV 后又发生变化，系统会要求重新回读和确认，避免把评价绑定到过期配置。配置被工程师修改不自动代表不满意；评价由工程师明确填写。

## 日志与案例证据

每个案例保存设计版本、确认状态、计划编号、阶段、执行状态、回读快照和评价。使用 `initialize_device(action="events", case_id=...)` 可以查看按时间排列的事件：设计更新、计划、执行、验证、人工复核、差异回读和反馈提交。事件只记录动作、阶段、结果、时间和关联编号，不记录密码、登录 Token、Cookie 或完整请求体。

设备配置快照保存在 SangforBox 本地计划与案例数据库中，用于复核实施前后差异；评价 CSV 由工程师填写后通过 MCP 保存。若需要诊断 AF 自身的流量日志、策略命中或系统日志，应先确认目标设备和手册中对应的只读接口，再通过 `query_device` 获取并关联案例编号。试用版尚未自动采集这些设备日志，也没有自动清理案例数据；实施结束后按项目的数据保留制度处理本地数据库和工程师保存的 CSV。

厦门出口测试环境可以验证工具调用、参数、阶段流程、回读与反馈机制。真实业务流量、默认建议是否合适及恢复路径，需要在本次现场实施中记录证据后评价。
