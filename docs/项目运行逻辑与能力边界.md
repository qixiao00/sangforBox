# SangforBox 项目运行逻辑与能力边界

## 1. 项目定位

SangforBox 是运行在工程师 Windows 电脑上的深信服 AF 本地运维工作台。它把设备凭据、本地手册知识库、AF HTTP API、变更计划、审核记录和结果文件统一封装在一个本地服务中，再通过网页和 WorkBuddy MCP 提供能力。

它本身不包含大模型。网页负责设备档案和运行状态管理；WorkBuddy 负责理解自然语言和组织对话；两个 Skill 只负责复杂场景的流程编排；所有真实设备读取和写入均由 SangforBox MCP 内置工具执行。

## 2. 整体运行链路

```text
工程师
  ├─ 本地网页 http://127.0.0.1:8765
  │    └─ 管理设备档案、测试连接、查看知识库和运行结果
  └─ WorkBuddy
       ├─ 普通对话：直接使用 af-workbench MCP
       ├─ 设备初始化：启用 af-device-initialization Skill
       └─ 应用控制优化：启用 af-app-control-optimization Skill
                         │
                         ▼
              SangforBox 本地服务
       FastAPI + Streamable HTTP MCP + SQLite
       ├─ 知识库：手册原文、API、CLI、FTS5 检索
       ├─ 设备档案：凭据由 Windows DPAPI 加密
       ├─ 运维工具：查询、计划、执行、回读
       ├─ 场景状态：初始化案例、应用控制审核记录
       └─ 输出文件：审核 CSV、问题 CSV、反馈 JSON、日志
                         │
                         ▼
                 AF 设备 HTTPS API
```
便携版运行后，数据全部位于 `SangforBox.exe` 同一目录：

```text
data\af.db             设备档案、知识库索引、初始化案例
data\policy-review.db  应用控制分析、审核和反馈记录
results\               审核 CSV、问题 CSV、反馈 JSON
logs\                  启动和 HTTP 访问日志
```

## 3. 基础能力

### 3.1 查询设备配置

适用于接口、区域、路由、网络对象、NAT、安全策略、应用控制策略、虚拟网线等实时状态查询。

```text
自然语言问题
  → 查找已注册查询能力 discover
  → 核对调用定义 describe
  → query_device 通过 AF HTTP API 读取
  → 返回与问题相关的配置、异常和结论
```

已注册的查询能力优先使用 `operation_id`。未注册但手册中存在的 GET 接口，可以先检索知识库，选定唯一 `endpoint_id` 后执行。结果必须区分“设备实测”“手册定义”和“推断”，不能把未读取到的数据当作正常。

### 3.2 编辑单项设备配置

适用于目标清楚、范围有限的新增、修改或删除，例如修改一个对象、接口或策略。标准链路是：

```text
discover / describe
  → prepare 获取必答问题
  → 工程师明确新增或修改、重名处理、启用状态等决定
  → plan 读取现状并生成持久化计划
  → 展示目标、步骤、影响、验证方式和回滚动作
  → 工程师明确确认当前 plan_id
  → apply 执行一次
  → query_device 回读验证
```

`plan` 只生成计划，不修改设备。写操作必须持有计划并得到明确确认；计划过期、设备现状变化或结果未知时不能盲目重试。同一计划通过原子状态控制避免重复下发。

## 4. 进阶场景一：应用控制策略优化

该场景处理整张应用控制策略表，目标包括命名规范、遮蔽与顺序问题、重复或合并候选、地址对象化，以及组合后的首条匹配效果复验。

```text
选择设备和分析方向
  → analyze_app_control 只读采集完整策略、对象和策略组
  → 异步分析并生成候选
  → 输出审核 CSV + 问题 CSV
  → 工程师逐项选择采纳 / 不采纳 / 待确认
  → review_app_control 固化审核版本
  → verify_app_control_review 重建整表并验证组合效果
  → preflight_app_control_review 重新读取设备、核对快照和阻断项
  → 工程师按工单手工修改设备
  → record_app_control_feedback 只读回采并生成差异 JSON
```

### 当前边界

- 当前支持分析、审核、组合复验、只读预检和人工实施后的反馈闭环。
- 当前没有应用控制优化专用的 `plan/apply` 执行适配器，不能自动写入设备。
- 不能把优化候选转交给通用 `edit_device` 绕过限制。
- `model_equivalent` 只表示在已声明模型前提下等价，不等于真实设备语义和生产流量已被证明等价。
- 设备快照变化后，旧审核失效，必须重新分析和审核。
- CSV 是审核材料，不是设备导入文件；工程师备注也不是执行指令。

## 5. 进阶场景二：设备初始化

该场景面向 AF 8.0.107 初始化试用，将目标设计、设备现状、分阶段变更、验证和现场反馈绑定到同一个 `case_id`。

```text
选择设备
  → design 建立初始化案例
  → inspect 完整盘点接口、区域、虚拟网线、对象、路由、NAT、安全和应用控制
  → 多轮补齐目标拓扑、接口用途、保护范围和默认选择
  → 工程师确认设计 revision
  → 按 management / topology / objects / routing / nat / security / application 分阶段处理
  → 每项执行 inspect → prepare → 单项 plan
  → 展示依赖、影响、验证标准和回滚动作
  → 工程师明确确认 plan_id
  → apply
  → verify 回读
  → 下一项或下一阶段
  → feedback_review / feedback_submit 汇总现场差异和满意度
```

### 当前边界

- 设备现状只能作为证据，不能替工程师决定目标拓扑、接口方向、保护范围、NAT 或默认策略。
- 设计必填信息和开放问题未清空前不能确认设计；设计修订后旧计划失效。
- 每个阶段一次只规划一个变更，上一项未验证前不能继续下一项。
- 虚拟网线、接口和区域必须作为依赖集处理，不能自行猜测解绑、迁移和删除顺序。
- 当前 Web API 地址所属管理接口禁止由初始化流程修改、删除、解绑或迁移；即使有备用路径也必须退出案例并由工程师带外手工处理。
- 无法从接口盘点中可靠识别当前 Web API 地址所属接口时，初始化流程禁止所有接口变更。
- 写入结果未知或回读不一致时立即暂停，由工程师核查并通过 `resolve` 记录人工结论。
- 配置回读一致只证明配置层一致，业务连通性仍需工程师现场验证。

## 6. 系统级安全边界

- 所有设备操作只走 SangforBox MCP 内置 AF HTTP API；不生成 Python、curl、PowerShell 直连脚本，也不自动切换 SSH/CLI。
- 凭据、登录和 Cookie 由本地服务管理；密码使用当前 Windows 用户的 DPAPI 加密，不通过 MCP 返回。
- 服务默认只监听 `127.0.0.1`，本身没有应用层身份认证；远程开放必须由 HTTPS 反向代理提供认证和访问控制。
- 本地知识库采用 SQLite FTS5 和中文分词，返回手册来源页码；当前没有向量 Embedding，也没有内置大模型问答。
- 未知字段、读取失败、分页不完整和不支持的设备语义不能被模型补全或当作成功。
- 任何生产写入都需要具体计划、明确确认和回读；结果未知时不得自动重试。
- WorkBuddy 中保存 MCP 表单不代表已经连通，必须用真实工具调用验证。

## 7. 四类用户提示词示例

### 基础查询

```text
查询“厦门出口”AF 的接口、区域和虚拟网线关系。只读取设备，不修改配置。先给结论，再用一张小表列出接口、工作模式、所属区域和依赖关系；区分设备实测与推断。
```

### 单项配置变更

```text
我要把“AF-Lab”上的网络对象 Office_Test 的地址修改为 10.20.30.0/24。先检查对象现状和引用关系，执行 prepare 并向我确认所有必答项，然后生成 plan，展示影响、验证方式和回滚动作。没有得到我对 plan_id 的明确确认前，不要执行 apply。
```

### 应用控制策略优化

```text
梳理“AF-Lab”的整张应用控制策略，检查命名、遮蔽、顺序、合并和地址对象化。先给我审核 CSV 和问题 CSV，不要修改设备。等我逐项决定后再做组合复验和只读预检；即使预检通过，也只输出工程师实施依据，不自动下发。
```

### 设备初始化

```text
为“AF-Lab”开始设备初始化。先建立 case，完整读取现有接口、区域、虚拟网线、路由、NAT、安全和应用控制配置，再根据缺失上下文逐轮询问我。不要根据接口名称猜内外网方向。设计需要我确认 revision；之后按阶段一次只生成一个 plan，每个 plan 都必须经我明确确认后才能 apply，并在执行后回读验证。
```
