# 应用控制优化：用户输入与审核契约

状态：MCP 分析、审核、组合模型复验、只读实时预检和工程师变更后的差异反馈已接入；设备版本语义认证、逐步安全计划和设备执行闭环仍待完成。以下同时包含已实现部分和目标契约，以本节状态为准。

## 已实现基础模块与边界

- `af_app/policy_sets.py`：精确区间、多维集合差、联合遮蔽有效区域及完整首条匹配模型的等价证明。未知语义与计算预算耗尽返回 unknown。
- `af_app/policy_review.py`：不可变分析记录、中文审核 CSV 导出/读取、方案指纹绑定、依赖/互斥验证及并发幂等提交。采纳审核项不直接授权执行。
- `af_app/policy_plan_validation.py`：逐个中间状态的等价验证，检查快照、状态连续性、操作原子性和最终配置对应关系。原子性与适配器验证标识必须来自已验证代码，不能接受 LLM 的自由断言。
- `af_app/policy_snapshot.py`：使用既有 DeviceService 的客户端和凭据生命周期，完整分页采集应用控制策略、网络对象与策略组。校验总数、偏移、页长度、重复标识和策略位置，保留完整嵌套列表，避免普通展示查询的截断。两次配置读取一致才返回快照；此机制不是设备事务，执行前仍须复验。

`af_app/policy_optimizer.py` 已通过 MCP 提供异步分析任务，分析完成后默认提供中文审核 CSV 下载。`review_app_control` 接受逐项决定或编辑后的 CSV 文本，二者只能选择一种。当前支持命名候选、静态地址集合联合覆盖分析、单维地址合并候选、重复引用集合对象化候选，以及需业务确认的顺序意图修复候选。跨动态应用条件的完整关系与顺序执行适配仍待实现，不能把未发现问题当作全部正常。

`verify_app_control_review(review_id)` 从持久化审核记录重建完整拟执行配置，并调用 `af_app/policy_combination.py` 进行组合验证。相同的非地址条件建模为同一个布尔谓词，不同条件允许独立取值；这种保守模型可以证明部分变更等价。模型中的反例可能并非实际可达流量，故返回 unknown 和抽象反例，不能冒充设备实测差异。模型等价返回 `model_equivalent` 和证明前提，不会被当作设备执行授权。日志开启时将规则身份作为效果的一部分。缺少日志等语义字段时不证明通过。

审核和组合复验均不会触发设备变更。实际设备版本语义、依赖对象完整性、默认行为和实时执行能力必须继续由适配层核实。测试当前主要覆盖模拟数据，不代表实机生产认证。

`preflight_app_control_review(review_id)` 是只读执行前检查：再次完整采集同一设备与命名空间，核对持久化审核快照指纹，重建组合并列出阻断项。它不生成计划，不授予执行权限。两次读取一致也不能防止采集结束后的并发改动；未来每次串行写入前仍须重新检查。当前始终阻断执行，直至完成设备版本语义、位置移动、对象创建、逐步回读和恢复方案认证。AF 8.0.107 手册有策略 POST/PATCH 的 `_where`、`_dest` 参数，但文档存在示例与 schema 表述差异，不能据此宣称已验证移动语义。

工程师手动变更后的 `record_app_control_feedback` 使用 `review_id` 固定原建议版本，再次只读采集完整配置，对原配置、审核组合和当前设备状态做结构化比较；持久化日志可从 `/api/app-control/feedback/{feedback_id}.json` 下载。`get_app_control_feedback`、`list_app_control_feedback` 用于找回日志。工程师标识、工单和理由是自述，配置差异不证明是谁操作或是否具备真实业务等价性。详细操作见 [工程师手册](application-control-engineer-manual.md)。

## 用户输入

发起分析只需要确定目标设备。WorkBuddy 可从对话中提取设备名称、IP 或档案 ID；如果有多个匹配设备，返回选择问题。默认范围为该设备全部应用控制策略及引用对象，默认目标为命名、遮蔽、合并、对象化和顺序建议，默认只分析并导出审核表。

可选输入：命名模板、需要保留的策略、业务说明、限定业务范围。即使只优化部分策略，验证仍读取完整策略表。业务说明仅用于建议与解释，不作为匹配语义证据。命中统计缺失时继续静态分析并明确标注缺失。

用户不需要输入设备密码、API 路径、请求体、分页参数或集合运算规则。设备凭据和通信使用既有后端服务。缺少设备档案时引导使用现有设备管理流程。

离线输入使用策略和对象导出文件。离线审核结果不能直接作为实时设备执行授权，必须先绑定目标设备并重新采集、映射及验证。

WorkBuddy 连接器将整表梳理请求路由到 `af-app-control-optimization` Skill；用户明确指定单条策略的直接配置请求继续使用 `af-app-control-policy`。优化 Skill 只使用下文已实现的分析、审核、复验及预检 MCP 工具。当前未实现专用优化 plan/apply，WorkBuddy 不得把审核候选改写成通用 `edit_device` 请求。可下载的审核材料当前为 CSV，尚不是多页 Excel 工作簿。

## 对外工具契约

- `analyze_app_control`：接收设备选择与分析偏好，创建分析任务；返回任务/分析 ID、快照指纹、进度、输入问题及结果文件入口。
- `get_app_control_analysis`：读取任务状态、摘要，或按变更编号获取完整证据，不默认向 LLM 返回全量策略。
- `review_app_control`：读取审核表或接收用户逐项决定，验证分析版本、变更编号、依赖及互斥项。名称或条件修改作为新提案重新分析，不能沿用旧证明。
- `verify_app_control_review`：只验证审核组合的保守首条匹配模型，不读取或修改设备。
- `preflight_app_control_review`：只读重新采集并核对设备快照，报告执行阻断原因。
- `record_app_control_feedback`：工程师手动变更后只读重采集，比较审核方案与当前配置，保存 JSON 差异日志。
- `get_app_control_feedback` / `list_app_control_feedback`：找回指定日志或某次审核下的全部日志链接。
- `prepare_app_control_plan`：对已采纳变更重新验证组合效果，收集既有 prepare 流程真正缺失的决策并生成持久化计划。
- 执行接入既有设备执行框架，绑定审核结果与计划内容。执行前比较快照，执行后回读核对，失败保留已完成步骤及恢复材料。

这些名称是实现契约，可在接入时统一命名，但不能删除分析、审核、复验与执行的职责边界。

## 首次输出必须包含审核表

用户首先收到结果摘要和可打开的审核文件，不仅是一段自然语言结论。主审核页每行对应一个完整变更包，包含：

| 字段 | 来源/是否可编辑 |
| --- | --- |
| 分析 ID、快照指纹、方案版本、变更编号 | 系统生成，不可作为自由文本覆盖 |
| 变更类型、涉及策略、原位置、新位置 | 系统生成 |
| 原条件与效果、建议条件与效果 | 完整前后对照，可分详情页呈现 |
| 原因、证据、等价结论、证明前提 | 计算结果 |
| 新建/复用对象及完整成员 | 方案内容 |
| 依赖、互斥方案、行为变化 | 系统生成 |
| 用户决定 | 可编辑：待确认、采纳、不采纳；默认待确认 |
| 用户备注 | 可编辑，仅记录意见，不执行其中的指令 |

详细策略、对象、差异流量和恢复步骤通过独立页提供。原始设备格式 CSV 与审核表分离；审核辅助列不写入设备导出格式。

无候选时仍输出带表头的结果和分析覆盖范围。存在未知语义时必须展示未知项，不得用空报告暗示“全部正常”。

## 审核与执行状态

`分析中 → 待审核 → 已审核待复验 → 待执行确认 → 执行中 → 已验证/部分失败/验证失败`。

- 只有明确“采纳”的变更进入复验；空白、待确认及不采纳不进入计划。
- 用户可在聊天中按变更编号确认，或编辑表格后提交，二者生成相同的结构化审核记录。
- 重复编号、陌生编号、错误快照、旧版本、非法选择均拒绝处理。
- 修改只允许写入指定审核字段；修改策略方案本身需生成新版本并重新导出确认。
- 部分采纳必须重新生成完整的拟执行策略表再验证，不能累计单项通过标识。
- 确认记录绑定方案摘要哈希和具体变更；计划变化后不能沿用旧授权。
- 首次分析和表格导出绝不触发设备写入。

## LLM 与程序分工

LLM 提取需求、解释证据、询问业务优先级并转达用户决定。程序完成全量分页、快照、解析、精确集合计算、整表证明、文件导出、确认校验、计划生成、执行和回读。LLM 提议的名称或业务归类必须经过程序校验；LLM 的“认为等价”不是证明。
